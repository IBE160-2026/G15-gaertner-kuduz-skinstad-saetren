# Spine Pair Review — Turnushjelperen

## Overall verdict
The spine pair is well-disciplined at the mechanical level: token frontmatter is complete and every `{path.to.token}` reference resolves, section order in both files matches the canonical/locked shape exactly, and the sole PRD user journey (UJ-1) is fully realized with protagonist, numbered steps, climax, and a failure path. A downstream consumer can source-extract the shape cleanly. The gaps are concentrated in coverage completeness and cross-file naming discipline: a few common UI states (login failure, AI-generation latency, an empty "nothing needs action" dashboard) are never specified; DESIGN.md never links to any of the six `.working/` mockups despite discussing them repeatedly; and two glossary/component names (`Innloggingskort` vs. `Innloggingsskjema`, `Kompetansenivå` vs. `kompetanse`) drift between the two files. None of this is broken — it is underspecified in ways a careful implementer would need to fill in by inference rather than by reading the spine.

## 1. Flow coverage — strong
PRD §2.3 names exactly one user journey, UJ-1 (Turnusansvarlig finner en erstatter for en vakt som mangler bemanning). EXPERIENCE.md's sole Key Flow is titled identically, keeps the protagonist name (Kari) and persona/context verbatim from the PRD, has 7 numbered steps, an explicit **Klimaks** beat (step 6, Kari overriding the top-ranked candidate), an **Oppløsning** beat (step 7), and a distinct **Edge case** paragraph (the "ingen gyldige kandidater" scenario, Vakt #4189) serving as the failure path. No FR is orphaned from the flow — all of FR-1, FR-2–FR-9, FR-11, FR-12 are touched by name or component within the flow's steps.

No misses found.

## 3. Component coverage — adequate
Every component named in DESIGN.md.Components has a corresponding EXPERIENCE.md.Component Patterns row with real behavioral rules (not one-word descriptions), with two exceptions.
### Findings
- **medium** Appbar has a full visual spec in DESIGN.md.Components (line 204: background, foreground, left/right content, "Ikke innlogget" variant) but no row in EXPERIENCE.md.Component Patterns — its only behavior (what shows pre- vs. post-login) is left to be inferred from the unrelated "Ikke innlogget / utløpt sesjon" row in State Patterns, which describes redirect behavior but not the appbar's own display rule. *Fix:* add an Appbar row to Component Patterns, or fold its one behavioral rule into the existing "Ikke innlogget" state row with an explicit pointer.
- **low** `rank-badge` (Rangeringsnummer) has a DESIGN.md visual row but no distinct Component Patterns row — defensible since it carries no behavior beyond static display, but it is folded silently into the Rangeringstabell row without a note. *Fix:* none required; optionally a one-line note in Rangeringstabell's behavioral rules acknowledging rank-badge has no independent behavior.

## 4. State coverage — thin
Walked all four IA surfaces (Logg inn, Vaktvalg, Kandidatrangering, Godkjenning) against empty/cold-load/focus/error/offline/permission-denied.
### Findings
- **high** Logg inn has no failed-authentication state anywhere in EXPERIENCE.md (State Patterns table only covers the reverse direction — "Ikke innlogget / utløpt sesjon" — which is about being redirected *to* Logg inn, not about what happens after a wrong username/password submission on that surface). FR-13 and the mockup (`.working/key-innlogging.html`) show only the populated, non-error form. *Fix:* add a State Patterns row for invalid credentials, even if minimal (e.g., inline field error, no lockout policy).
- **medium** Kandidatrangering has no cold-load/computing state. FR-1's consequence explicitly says filtering+ranking starts "uten ytterligere handling," and FR-11 generates an AI explanation per candidate — both are workloads with real latency, yet the only Kandidatrangering-related row in State Patterns is "KI-forklaring feilet/tom/ubrukelig," which addresses failure but not the wait between clicking "Velg vakt" and the ranked table rendering. *Fix:* add a loading/computing state row, distinguishing rule-engine latency (likely fast) from AI-explanation latency (likely slower, may need per-row progressive reveal).
- **medium** Vaktvalg has no "ingen vakter krever handling" empty state. The only Vaktvalg row in State Patterns and the only mockup (`key-vaktvalg.html`) show exactly one flagged vakt; nothing specifies what the dashboard shows when zero vakter need action (empty "Krever handling" section, or the section hidden entirely). *Fix:* add a State Patterns row for the zero-flagged-vakt case.
